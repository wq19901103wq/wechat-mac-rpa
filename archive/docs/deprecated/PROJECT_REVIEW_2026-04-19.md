# 微信 Mac RPA 项目审查报告

> 审查日期：2026-04-19
> 审查范围：架构设计、代码质量、工程实践、运维安全
> 审查人：AI Assistant

---

## 执行摘要

本项目是一个基于 Vision OCR 的微信 Mac 自动化方案，采用 L1-L5 分层架构。整体设计思路清晰，但在**文档与代码同步**、**工程化完备性**、**可观测性**等方面存在显著改进空间。

### 关键结论

- ✅ **核心架构合理**：Vision OCR 避免了 SIP/数据库解密的复杂性
- ⚠️ **文档债务严重**：目标架构与实际代码脱节
- 🔴 **工程化缺失**：无进程管理、日志轮转、健康检查
- 🔴 **安全隐患**：明文存储聊天记录、权限过大

## 一、架构设计分析

### 1.1 设计合理之处

| 方面 | 评估 | 说明 |
|------|------|------|
| 分层架构 | ✅ 良好 | L1-L5 分层（Domain → Capture/OCR → Layout → Session/Reply/Action → Bot）清晰合理 |
| 技术选型 | ✅ 优秀 | Vision OCR 方案避免 SIP/数据库解密，安全稳定 |
| 可观测性设计 | ✅ 良好 | runtime.log + execution.jsonl 双轨日志设计 |
| 去重机制 | ⚠️ 可改进 | MessageIdentity 设计合理，但实现有待优化 |

### 1.2 架构设计缺陷

#### 🔴 缺陷 1：目标架构与实际代码严重脱节

**问题描述**：

```
文档描述（ARCHITECTURE.md）:        实际代码:
src/layout/layout_parser.py   ❌ 不存在
src/message/extractor.py      ❌ 不存在
src/reply/policy.py           ❌ 不存在
src/reply/generator.py        ❌ 不存在

实际存在:
src/parser/wechat_parser.py   ✅ 统一处理解析
src/action/reply_generator.py ✅ 策略与生成混在一起
```

**影响**：
- 新开发者按文档找不到对应文件
- 维护困难，代码阅读成本高
- 架构文档失去参考价值

**建议**：
1. 方案 A：重构代码以匹配文档（成本高，风险大）
2. 方案 B：删除文档中的"目标架构"章节，重写为"当前实现"（推荐）

#### 🟡 缺陷 2：缺乏分层接口契约

**问题描述**：
- VisionPipeline 输出格式没有 schema 校验
- 各层间数据流转依赖隐式约定
- 缺乏接口版本管理

**建议**：
- 为关键接口添加 Pydantic 模型验证
- 添加层间契约测试

## 二、代码质量问题

### 2.1 魔法数字与硬编码

```python
# src/layout/profile.py
TITLE_Y_MAX = 50              # 为什么是50？
TITLE_X_MAX_RATIO = 0.70      # 为什么是0.70？
INPUT_Y_MIN = 1160            # 为什么是1160？

# 注释:"基于 N=50 个样本的 P95 值"，但缺乏:
# - 样本数据在哪里？
# - 如何重新校准？
# - 不同微信版本是否需要不同值？
```

**风险**：微信版本更新后边界值可能失效，且无法追溯调整依据。

### 2.2 异常处理不完善

```python
# 多处 try/except pass 吞掉错误
try:
    action_result = self.sender.send(reply)
except Exception:
    pass  # ❌ 错误被静默忽略
```

**风险**：发送失败无法感知，导致消息丢失。

### 2.3 路径硬编码

```python
# 多处重复硬编码
"~/wechat-mac-rpa/data/screenshots/"
"~/wechat-mac-rpa/data/logs/"
```

**建议**：统一使用配置管理（如 `pydantic-settings`）。

## 三、功能缺陷

### 3.1 OCR 识别准确率瓶颈

| 问题 | 案例 | 频率 | 影响 |
|------|------|------|------|
| 昵称识别错误 | "SampleUser" → "®v QS." | 偶发 | 消息归属错误 |
| 时间戳混入消息 | "00:04" 被识别为消息内容 | 常见 | 消息序列错乱 |
| 输入框内容残留 | 上次输入被识别为新消息 | 常见 | 误回复 |
| 头像数字噪声 | 未读数被识别为消息 | 偶发 | 假消息 |

**根本原因**：
- 边界值基于经验而非系统校准
- 缺乏多微信版本的适配测试

### 3.2 去重机制缺陷

**当前实现**：基于 y坐标 + 时间窗口

**问题场景**：
```
聊天窗口滚动后，同一条消息的 y 坐标发生变化，
导致 filter_new() 认为这是新消息，重复回复。
```

**文档承诺**：
> "用'窗口指纹 + 上下文序列'替代 Y 坐标去重"

**实际情况**：未实现，仍为 y坐标去重。

### 3.3 性能瓶颈

```
总耗时: ~17.5s
├─ 截图: 0.325s (4.5%)
├─ OCR: 1.02s (14.2%)
├─ Layout解析: 2.6s (36.3%) ✅ 已优化
├─ LLM生成: 10.35s (44.6%) ← 最大瓶颈
└─ 发送: 0.5s (2.2%)
```

**问题**：
- LLM 调用同步阻塞，无法并发处理多聊天
- 没有流式响应，用户感知延迟长
- 没有本地规则兜底（简单问题也走 LLM）

## 四、工程化缺失

### 4.1 进程与生命周期管理

| 能力 | 现状 | 期望 |
|------|------|------|
| 进程管理 | 无，直接 python 运行 | systemd/supervisor 托管 |
| 崩溃重启 | 无 | 自动重启 + 告警 |
| 健康检查 | 无 | /health 端点 |
| 优雅关闭 | 无 | SIGTERM 处理 |

**风险**：进程崩溃后无人知晓，漏掉重要消息。

### 4.2 日志管理

**现状**：
- runtime.log 无限追加
- 没有日志轮转
- execution.jsonl 无限增长

**风险**：长期运行磁盘占满。

**建议**：
```python
# 添加日志轮转
from logging.handlers import RotatingFileHandler
handler = RotatingFileHandler(
    "runtime.log", maxBytes=5*1024*1024, backupCount=3
)
```

### 4.3 配置管理

**现状**：
- .env 文件
- 硬编码值
- config/ 目录（可能还有）

**问题**：配置来源分散，缺乏统一管理和验证。

**建议**：使用 `pydantic-settings` 统一管理。

## 五、安全与隐私风险

### 5.1 数据安全

| 风险 | 现状 | 建议 |
|------|------|------|
| 聊天记录存储 | 明文 JSONL | 加密存储 |
| 截图保存 | 无自动清理 | 定期清理 + 加密 |
| API Key 管理 | .env 文件 | 密钥管理服务 |
| 传输安全 | 无（本地） | 如需云端传输，启用 TLS |

### 5.2 权限安全

**问题**：AppleScript 可以控制整个 macOS 系统。

```python
# 当前实现
script = f'''
tell application "System Events"
    keystroke "v" using command down
end tell
'''
osascript(script)  # ⚠️ 权限过大
```

**建议**：
- 考虑使用更受限的辅助功能 API
- 添加操作审计日志

### 5.3 隐私合规

**问题**：
- 聊天内容通过 LLM API 发送到云端
- 没有数据脱敏
- 没有用户授权确认

**建议**：
- 添加敏感信息过滤（手机号、身份证号等）
- 提供本地 LLM 选项（如 llama.cpp）

**现状**：硬编码 Kimi/OpenAI，切换成本高。

**建议**：抽象 LLM 接口，支持多供应商。

**现状**：
- Prompt 散落在代码中

**建议**：

# 使用 Prompt 管理工具

├── system_v1.txt
├── system_v2.txt

### 7.3 费用失控风险

**现状**：
- 没有 Token 用量监控
- 没有费用上限保护
- 简单问题也走 LLM

**建议**：
- 添加 Token 计数器
