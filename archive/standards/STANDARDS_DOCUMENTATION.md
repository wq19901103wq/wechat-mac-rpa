# 文档守则

> 适用于：任何修改架构、接口、流程、配置或修复 bug 后需要更新文档的场景。
> 
> 核心原则：**文档是代码的一部分。修改代码而不同步更新文档，等同于提交不完整的工作。**

---

## 📄 任何代码变更必须同步更新文档

以下情况必须同步更新文档：

| 变更类型 | 必须更新的文档 |
|---------|--------------|
| 新增/删除模块 | `ARCHITECTURE.md` |
| 接口签名变更 | `API_SURFACE.md` |
| 新增/修改文件职责 | `MODULE_INDEX.md` |
| 上手流程或配置变化 | `AI_QUICKSTART.md` |
| 日志/存储结构变化 | `LOGGING_DESIGN.md` |
| 踩到新坑或验证旧假设 | `LESSONS_LEARNED.md` |
| 修复已知错误 | `STANDARDS_TESTING_BUGS.md` 的"当前待修复错误"清单 |

**禁止行为**：
- ❌ 架构已经改了，`ARCHITECTURE.md` 还是旧版
- ❌ 错误已经修复，但守则里还标着"待修复"
- ❌ 新增模块但 `MODULE_INDEX.md` 里没有索引

---

## 📐 文档内部自洽禁令

任何描述接口或架构的文档，自身必须逻辑一致，禁止"文档打自己的脸"。修改文档时，必须同时检查：

1. **接口声明与调用示例一致**。若 `def foo(a: str, b: int)`，示例中不得出现 `foo(x)` 或类型 mismatch。
2. **伪代码必须和文字描述一致**。注释说"时间窗口优先"，伪代码就不能还是旧版坐标匹配。
3. **引用的函数/类必须在文档内有定义或链接**。禁止出现从未解释的 `estimate_y()` 这类黑盒函数。
4. **命名必须统一**。同一文档中不得前面叫 `OCREngine`、后面叫 `VisionOCREngine`。

**禁止行为**：
- ❌ 文档内部接口声明和调用示例自相矛盾
- ❌ 伪代码逻辑与文字说明不一致
- ❌ 文档中引用未定义的函数或类

---

## 🏗️ 设计文档与实现代码的审查边界

`ARCHITECTURE.md` 等设计文档的定位是**让 AI Agent 在 5 分钟内理解系统结构**，不是可执行源码。Review 或修改时必须遵守以下边界，避免过度审查实现细节：

| 属于设计文档的职责 ✅ | **不属于**设计文档的职责 ❌ |
|----------------------|---------------------------|
| 模块划分与依赖方向 | `import` 语句是否齐全 |
| 数据流与主循环逻辑 | 运行时状态（如 `self.running`）的初始化 |
| 关键算法思路（去重、检测等）| 标准库函数（如 `md5`、`time`）是否已 import |
| 接口签名与参数语义 | 详细的异常处理、日志输出、性能优化 |
| 架构决策的理由与权衡 | 单元测试的具体 assert 内容 |

**AI Review 时的判断标准**：
- 如果一个问题会导致"按文档实现的人误解系统设计"，则必须修。
- 如果一个问题只是"按文档直接复制粘贴无法运行"，但意图清晰，则**不应**要求文档修改（这是代码和 API_SURFACE.md 的职责）。
- 如果文档里有**硬编码的魔法数字**，必须抽提到 `LayoutProfile` 或相应配置层。
- 如果文档提到了一个函数/常量/模式但**从未解释它是什么**，必须补充说明。

---

## 📊 文档必须标注实现进度

任何文档、设计说明、架构图、API 定义，如果描述的内容尚未完全落地，必须明确标注其状态。禁止用"已完成""已落地""V2 完成"等模糊词汇掩盖未实现的部分。

强制使用以下标签之一（在文档顶部用 `> ` 引用块标注）：

| 标签 | 含义 | 示例 |
|------|------|------|
| **🚧 未实现** | 仅设计/规划阶段，代码不存在或为空壳 | `src/perception/vision_pipeline.py` |
| **📝 开发中** | 代码已部分实现，但尚未完成或不稳定 | `src/layout/` 拆分 |
| **✅ 开发完成** | 代码已实现，但尚未通过完整测试 | 新模块刚合并到 feature branch |
| **🧪 测试完成** | 已通过测试，但尚未合并到主分支/线上 | CI 全绿待 review |
| **🚀 已上线** | 已在主分支/生产环境稳定运行 | `src/bot/wechat_bot.py` |

**适用场景**：
- `ARCHITECTURE.md`、`API_SURFACE.md`、`MODULE_INDEX.md` 等目标架构文档 → 必须标注 "⚠️ 目标重构架构（Target Architecture），当前实际代码与此存在差异"
- 任何涉及"下一步""未来""待实现"的章节 → 必须标注对应进度标签
- 方案对比、功能列表、版本说明 → 必须标注各功能/版本的实际状态

**禁止行为**：
- ❌ 目标架构文档不标注"目标架构/尚未实现"
- ❌ 设计文档和实际代码状态出现显著差距而不更新标注
- ❌ 用"模块化架构 V2 完成"等表述掩盖目标架构与当前代码的不一致

## ✅ 改文档前的强制检查

每次修改架构/接口文档时，必须执行以下步骤：

1. **运行自动化检查脚本**（不可跳过）：
   ```bash
   python3 scripts/doc_lint.py
   ```
   如果脚本报错，必须修复文档直到全绿，才能提交。

2. **人工强制复核**（不可省略）：
   - [ ] **接口签名改了** → `grep` 全文搜索旧名称，确保示例/伪代码/引用全部更新
   - [ ] **新增/删除了类型/模块** → 检查层级依赖规则（L4 不能引用 L3 内部类型）
   - [ ] **新增/删除了配置项** → 检查 `LayoutProfile` 或对应 L4 模块是否同步
   - [ ] **改了架构分层** → 检查 ASCII 图和依赖规则是否同步
   - [ ] **`API_SURFACE.md` 里有接口定义** → 运行"可复制粘贴测试"：检查 `NameError`（缺失 import、未定义类型等）
   - [ ] **`ARCHITECTURE.md` 里有伪代码** → 快速扫未定义的变量/常量、无限增长的集合、缺少 `pass` 的方法体、未初始化的 `self.xxx`
   - [ ] **`ARCHITECTURE.md` 引用了类型/常量** → 只需确保在当前文档内有定义或显式解释，不要求 import 语句齐全
   - [ ] **新增扩展点** → 确认所需字段/接口已存在，不是空中楼阁
   - [ ] **新增回调/事件** → 检查构造函数是否赋值、主循环是否调用、API_SURFACE 是否同步
   - [ ] **新增/删除了文件** → 同步检查第七节文件结构树和 `MODULE_INDEX.md`
   - [ ] **`ARCHITECTURE.md` 改了** → 同步检查 `API_SURFACE.md`
   - [ ] **`API_SURFACE.md` 改了** → 运行"可复制粘贴测试"：将所有代码块复制到一个临时 `.py` 文件中，检查 `NameError`（缺失 import、未定义类型等）
   - [ ] **引用了常量/模式**（如 `TIMESTAMP_PATTERNS`）→ 确认在当前文档内有定义或显式链接，不能依赖其他文档

> ⚠️ **注意**：`doc_lint.py` 只能覆盖签名一致性和未定义标识符，**无法检测**：伪代码逻辑完整性、构造函数内部赋值、回调在主流程中的调用、分层依赖违规、文件树遗漏、常量未定义。这些必须靠人工复核。
> 
> **设计文档 vs 接口文档的边界**：`ARCHITECTURE.md` 是设计文档，不要求可执行，只需意图清晰；`API_SURFACE.md` 是接口契约文档，才需要做完整的可复制粘贴测试。
