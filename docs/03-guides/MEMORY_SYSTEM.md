# 微信 Bot 记忆系统设计文档

## 1. 概述

当前 Bot 仅有短期工作记忆（GlobalStore 保存最近 200 条原始消息），存在以下问题：
- 没有"理解层"：存的是原始文本，不是结构化知识
- 不会主动使用：历史消息堆在 prompt 里，AI 不一定注意到关键信息
- 跨会话断层：换个聊天或重启后，之前的话题可能重复提起
- 没有用户画像：Bot 对每个人都是一样的

本方案采用 **LLM Wiki** 模式：让 LLM 用自然语言自主维护每用户/每群的知识文章，代码层只负责读写文件和调度更新。

---

## 2. 设计原则

| 原则 | 说明 |
|---|---|
| **LLM 自维护** | 知识怎么组织、什么该记、什么该删，由 LLM 自己决定 |
| **三维信息** | 每条记忆必须包含：会话（哪里说的）、发送者（谁说的）、时间（什么时候说的） |
| **按聊天分离** | 私聊记忆绑定个人，群聊记忆绑定群 + 群内个人片段 |
| **可人工干预** | wiki 是纯 Markdown，用户可以直接打开修改 |
| **异步更新** | 更新 wiki 不阻塞消息发送，后台处理 |

---

## 3. 系统架构

```
┌─────────────────────────────────────────────────────────┐
│  超短期 SessionMemory（跨 tick 缓存）                    │
│  - 工具执行结果缓存（web_search、stock_query 等）        │
│  - 按聊天隔离，带 TTL（搜索 5min、股价 1min）            │
│  - 避免同话题下重复调用工具                               │
├─────────────────────────────────────────────────────────┤
│  短期工作记忆（GlobalStore）                             │
│  - 最近 200 条原始消息                                   │
│  - 用于当前 tick 的上下文和去重                          │
├─────────────────────────────────────────────────────────┤
│  LLM Wiki 长期记忆                                       │
│  ├─ users/   个人 wiki（私聊 + 群聊中该用户的信息）       │
│  ├─ groups/  群聊 wiki（群规、近期话题、接龙记录）        │
│  └─ topics/  话题 wiki（跨用户的公共知识，如餐厅信息）    │
├─────────────────────────────────────────────────────────┤
│  记忆引擎（MemoryEngine）                                │
│  - 增量更新：每次对话后调 LLM 更新 wiki                   │
│  - 定期整理：每天凌晨让 LLM 压缩、归档过期内容            │
│  - 查询检索：根据当前聊天对象和关键词取出相关 wiki         │
└─────────────────────────────────────────────────────────┘
```

## 5. SessionMemory（超短期记忆）

`src/reply/session_memory.py`

### 5.1 作用
跨 tick 缓存工具执行结果，避免同个聊天中短时间内重复调用相同工具。

### 5.2 缓存策略

| 工具 | TTL | 说明 |
|------|-----|------|
| `web_search` | 5 分钟 | 搜索结果短期内有效 |
| `stock_query` | 1 分钟 | 股价变化快，缓存时间短 |
| `get_weather` | 30 分钟 | 天气预报短期内不变 |
| `search_memory` | 10 分钟 | wiki 记忆短期内不变 |
| `get_current_time` | 不缓存 | 每次都查最新时间 |

### 5.3 注入 Prompt

缓存结果作为第二条 system message 注入：

```
已缓存数据（来自之前查询，无需重复调用）
- web_search("小米股价") [16:20 缓存，剩4分钟] → 小米集团今日...
- stock_query("sh600519") [16:18 缓存，已过期]
```

LLM 看到缓存后知道之前搜过什么，不需要再次调用工具。

## 6. 更新流程

### 5.1 触发时机

| 时机 | 操作 | 优先级 |
|---|---|---|
| **每次 Bot 回复后** | 把本轮对话加入增量更新队列 | 高 |
| **队列满 3 条或超 5 分钟** | 调 LLM 执行批量增量更新 | 高 |
| **每天凌晨 4:00** | 调 LLM 做全量整理（压缩、归档、删除过期） | 低 |
| **用户说"忘掉 XXX"** | 人工触发，从 wiki 中删除指定段落 | 高 |

### 5.2 增量更新 Prompt

```
请根据以下对话记录，更新用户 wiki。

【现有 wiki】
{current_wiki}

【新对话】
聊天：{chat_name}（{chat_type}）
时间：{current_time}

对话内容：
{conversation}

【更新规则】
1. 只修改/新增变化的部分，保留未变动的内容
2. 区分信息来源：私聊内容 confidence 高，群聊内容 confidence 中
3. 标注日期：时间敏感的信息必须带日期
4. 过期处理：超过 7 天的"近期动态"移到"历史归档"或删除
5. 冲突处理：新信息覆盖旧信息，旧信息保留在"历史归档"
6. 不确定的信息用 [待验证] 标记

【输出】
直接输出更新后的完整 wiki markdown，不要加代码块标记。
```

### 5.3 全量整理 Prompt（每日）

```
请整理以下 wiki，使其简洁、准确、无冗余。

【待整理 wiki】
{current_wiki}

【整理规则】
1. 合并重复或相似的内容
2. 删除已过期的事项（如"明天去XX"已过日期）
3. 把"近期动态"中超过 30 天的内容移到"历史归档"
4. 控制长度：个人 wiki 不超过 1500 字，群聊 wiki 不超过 1000 字
5. 保持 Markdown 格式

【输出】
整理后的完整 wiki。
```

## 6. 使用流程（注入 Prompt）

### 6.1 查询策略

生成回复前，根据当前场景取出相关 wiki 内容：

```python
def get_relevant_memory(chat_name: str, sender: str, unread_texts: List[str]) -> str:
    """取出与当前场景相关的记忆片段"""
    parts = []
    
    # 1. 当前用户的个人 wiki（全文或摘要）
    user_wiki = load_user_wiki(sender)
    parts.append(f"【关于对方】\n{compress_wiki(user_wiki, max_chars=400)}")
    
    # 2. 当前群聊的 wiki（如果是群聊）
    if is_group_chat(chat_name):
        group_wiki = load_group_wiki(chat_name)
        parts.append(f"【本群近况】\n{compress_wiki(group_wiki, max_chars=200)}")
    
    # 3. 话题 wiki（未读消息中提到的关键词匹配）
    for keyword in extract_keywords(unread_texts):
        topic_wiki = load_topic_wiki(keyword)
        if topic_wiki:
            parts.append(f"【关于{keyword}】\n{compress_wiki(topic_wiki, max_chars=150)}")
    
    return "\n\n".join(parts)
```

### 6.2 注入位置

把记忆内容放在 **system prompt 之后、user prompt 之前**，作为上下文背景：

```
system: 你没有固定人设...

memory: 【关于对方】
        - 林岚，上海人，程序员...
        
        【本群近况】
        - 最近讨论海王盛宴...

user: 【消息上下文】...
      【未读消息】...
```

### 6.3 长度控制

| 记忆类型 | 最大注入长度 |
|---|---|
| 个人 wiki | 400 字 |
| 群聊 wiki | 200 字 |
| 单个话题 wiki | 150 字 |
| **总计** | **≤800 字** |

超出时，让 LLM 先对 wiki 做摘要压缩，再注入。

## 7. 持久化与生命周期

### 7.1 文件持久化

- wiki 文件实时写入磁盘（每次更新后立即保存）
- 格式：UTF-8 Markdown
- 备份：每天凌晨整理前自动备份一份到 `data/memory/backup/`

### 7.2 生命周期管理

| wiki 区域 | 生命周期 | 管理方式 |
|---|---|---|
| 近期动态 | 30 天 | 每日整理时移入"历史归档"或删除 |
| 说过的话（短期） | 7 天 | 每日整理时清理 |
| 偏好/兴趣 | 永久 | 除非用户明确说"不再喜欢" |
| 基本信息 | 永久 | 新信息覆盖旧信息 |
| 历史归档 | 90 天 | 超期删除 |

### 7.3 记忆衰减可视化

```
活跃度
  1.0 ┤    ★ 偏好/基本信息（永久）
      │
  0.8 ┤
      │   ╲  ★ 近期动态（30天线性衰减）
  0.5 ┤    ╲
      │     ╲  ★ 说过的话（7天快速衰减）
  0.2 ┤      ╲
      │       ╲─── 移入历史归档
    0 ┤────────────────────────→ 时间
```

**交互流程**：
1. `ReplyGenerator.generate()` 调用前，`MemoryEngine.get_relevant_memory()` 取出相关 wiki
2. wiki 内容注入到 prompt 中，作为 LLM 的上下文背景
3. LLM 生成回复的同时，`MemoryEngine` 把本轮对话加入增量更新队列
4. 队列满足条件后，异步调 LLM 更新 wiki 文件
5. 回复生成器支持双模型路由：简单任务走 `llm_client`（OpenClaw/Kimi），复杂任务（带 skill/tool 匹配）走 `complex_llm_client`（Hermes）

## 9. 隐私与边界

### 9.1 信息隔离

- **私聊信息**：只写入该用户的个人 wiki，其他用户不可见
- **群聊信息**：只写入群 wiki 和说话者本人的个人 wiki
- **跨群隔离**：A 群聊的内容不会出现在 B 群的 wiki 中

### 9.2 敏感信息处理

- 密码、手机号、地址等敏感信息，LLM 更新时自动脱敏（用 [敏感信息] 替换）
- 用户说"忘掉这个"时，立即从 wiki 中删除
