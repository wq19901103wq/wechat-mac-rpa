# 代码审计工作流

> 目标：全库代码审查发现的每一条问题，都必须经过"记录 → 人工 Review → AI 迭代 → 确认执行 → 回归验证"的完整闭环，才能标记为 fixed。

---

## 工作流全景

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  1. 发现问题   │ ──→ │ 2. 录入系统   │ ──→ │ 3. 标记状态   │
│ (人工审计/工具)│     │ (code_audit表)│     │ (页面操作)   │
└─────────────┘     └─────────────┘     └──────┬──────┘
                                               │
                         ┌─────────────────────┘
                         │
              ┌──────────▼──────────┐
              │   status = rethink   │
              │   notes = 点评/要求   │
              └──────────┬──────────┘
                         │
                         ▼
              ┌─────────────────────┐
              │ 4. 用户复制 notes    │
              │    发给 Kimi 对话    │
              └─────────────────────┘
                         │
                         ▼
              ┌─────────────────────┐
              │ 5. Kimi 回复修复方案 │
              └─────────────────────┘
                         │
                         ▼
              ┌─────────────────────┐
              │ 6. 粘贴到「AI方案」  │
              │    保存到 ai_proposal│
              └──────────┬──────────┘
                         │
              ┌──────────▼──────────┐
              │    7. 人工 Review    │
              │   方案是否满意？      │
              └──────────┬──────────┘
                         │
         ┌───────────────┴───────────────┐
         │                               │
    ❌ 不满意                          ✅ 满意
         │                               │
         ▼                               ▼
  修改 notes（提新要求）           点击「确认执行」
         │                               │
         └──────────────→ status = todo
                         │
                         ▼
              ┌─────────────────────┐
              │ 8. 人工执行修复代码  │
              │   (AI 辅助/手动修改) │
              └──────────┬──────────┘
                         │
                         ▼
              ┌─────────────────────┐
              │ 9. 回归验证          │
              │   pytest + Playwright│
              └──────────┬──────────┘
                         │
                         ▼
              ┌─────────────────────┐
              │ 10. 标记 fixed       │
              └─────────────────────┘
```

**核心原则**：人工可以多次不满意，循环直到改出满意结果为止。

---

## 状态定义

| 状态 | 含义 | 可流转至 |
|------|------|----------|
| `pending` | 待处理，未开始 Review | rethink, todo, wontfix, deferred |
| `rethink` | 需要 AI 重新思考/给方案 | todo（确认执行后）|
| `todo` | 方案已确认，待人工修复 | fixed |
| `fixed` | 已修复并通过回归验证 | - |
| `wontfix` | 不需要修复 | - |
| `deferred` | 搁置，后续处理 | - |

---

## 字段说明

| 字段 | 用途 |
|------|------|
| `status` | 当前流转状态 |
| `notes` | 人工点评/给 AI 的要求/反馈（人机对话中"人"的话）|
| `ai_proposal` | AI 回复的修复方案（人机对话中"机器"的话）|

---

## 人机循环细节

### Round N（第一次 or 第 N 次迭代）

1. **人**：在页面写 `notes`（如："时间戳解析不要 hardcode 格式，要支持相对时间"）
2. **人**：把 `notes` 内容复制，粘贴到 Kimi 对话发送
3. **AI（Kimi）**：回复修复方案
4. **人**：把方案粘贴到页面「AI 方案」框，保存到 `ai_proposal`
5. **人**：Review 方案
   - **不满意**：修改 `notes`（如："还要考虑时区问题"）→ 回到步骤 2，开始 Round N+1
   - **满意**：点击「确认执行」→ `status` 变为 `todo`

### 为什么不用"生成 Prompt"按钮

用户的点评（`notes`）本身就是给 AI 的指令，不需要额外包装。直接复制粘贴到 Kimi 对话即可，减少无效步骤。

---

## 执行修复前的强制检查

点击「确认执行」前，系统校验：

- [ ] `status` = `rethink`
- [ ] `ai_proposal` 非空（必须有 AI 方案）
- [ ] `notes` 非空（必须有 Review 意见）

满足条件才允许流转到 `todo`。

---

## 回归验证清单

修复完成后，必须跑以下测试：

1. **后端**：`pytest tests/test_api_*.py` — 验证 API 逻辑正确
2. **前端**：`pytest tests/e2e/` — 验证页面交互正常
3. **业务**：针对本次修复的具体场景，补充对应的断言

全部通过 → 在页面标记 `fixed`。
