# 回复质量评价体系

> **历史口径，不再控制当前 Judge/C0 数据划分与采用门槛。** 现行唯一流程见 `JUDGE_C0_CANONICAL_WORKFLOW.md`；若本文的 40 场景、参与判断或多 Benchmark 口径与其冲突，以现行流程为准。

## 核心标准

评价对象是真人实际看到的完整聊天，不是脱离语境的单句。Bot 应像这个聊天关系里的真人：理解当时的人、指代、时间和话题，并带来合适的信息、情绪或推进价值。

- `好`：符合关系和语境，并明显带来信息、情绪或话题推进价值。
- `可接受`：符合语境、没有明显问题，但价值有限。
- `差`：不该回复、没接住、机械客套、低价值抢话、旧梗复用、跨回合重复或表达不像该聊天中的真人。
- `严重问题`：有上下文证据支持的严重身份、对象、事实或边界错误。关键词本身不能直接判严重。

判定顺序：先判断此刻是否该回复，再判断是否理解语境，然后判断价值和真人感，最后检查旧梗、重复、事实与边界风险。

## 真人聊天参照

每次基线都从全部历史真人消息重新提取群聊和私聊参照，包括消息长度、短消息比例、问句比例、口语比例、表情比例和粗话比例。评价 Bot 时使用对应聊天的真人参照，不能套用礼貌客服标准。

粗话、互损和攻击性可能是熟人聊天的正常风格，不因词面自动扣分；是否有问题取决于关系、对象、上下文和真人后续反应。旧梗和跨回合重复仍是质量问题。

历史快照会反复包含同一条真人消息，无法可靠区分“真人再次说了同一句”和“同一消息被再次截取”，所以首版不报告真人重复率。Bot 的真实发送按独立回合记录，可以筛查其跨回合内容复用。

## 两个回路与三个 Benchmark

评价系统严格按 README 的数据飞轮分成三层，不能混用：

1. **Human Gold benchmark**：真人查看完整上下文，标注该回复还是沉默、四档体验等级和理由。这是质量定义本身。
2. **Judge Quality benchmark**：同一批 case 交给 Judge，比较它与 Human Gold 的回复决策、体验等级、坏回复识别和严重问题召回。未通过时，Judge 不能评价 Bot 实验。
3. **Bot A/B benchmark**：当前版与实验版在同一批固定场景多次作答，隐藏版本并随机左右顺序，由已校准 Judge 做配对判断。

因此执行顺序固定为：`真人 Gold → Judge 校准通过 → Bot A/B`。任何前置门禁未通过，后续报告只能显示 pending/blocked，不能给出“新版更好”的结论。

固定场景生成后，可从全部历史场景中按“回复/沉默 × 群聊/私聊”稳定抽取首批待标 Gold：

```bash
python scripts/prepare_reply_quality_gold.py --sample-size 40
```

无法区分“模型主动沉默”和“发送失败”的历史行为会被排除。生成的公开清单不含聊天正文；私有待标包权限为 `600`，其中所有真人结论初始均为 `pending`，不会伪造缺失理由。

本地评审页：

```bash
python scripts/review_reply_quality_gold.py
```

访问 `http://127.0.0.1:8767`。该服务只操作本地私有 Gold 文件，不启动 Bot、不连接微信、不调用模型；动作、四档等级和理由不完整时拒绝保存。

## 证据分层

四类信息必须分开保存，禁止相互冒充：

1. `historical_reaction_evidence`：回复后真人继续、正向、纠正、反感或没有可见反应。
2. `ai_provisional`：按固定规则生成的首轮暂定判断，只用于全量筛查。
3. `human_ground_truth`：真人逐条确认后的金标准，发布比较以它为准。
4. `judge_fact_safety`：Judge 对事实和边界风险的辅助提示，不进入体验总等级。

AI 暂定判断和关键词信号都不能宣称是最终真人质量分。

## 评测对象

当前系统质量不能由历史 169 个发送回合直接代表。历史回复只承担三种作用：提供真实聊天场景、提炼真人表达参照、保留旧系统对照证据。正式评测必须让当前完整回复链路在固定场景中重新决定“回复或沉默”，并生成候选回复。

```bash
python scripts/prepare_reply_system_benchmark.py
```

该命令只准备固定场景，不启动 Bot、不发送消息、不调用模型：

- `data/reports/reply_system_benchmark.json`：可公开的场景清单与评测状态，不含聊天正文。
- `data/reports/private/reply_system_scenarios.json`：本地私有场景包，包含当前系统回放所需上下文。

刚生成时 `current_system_baseline.status` 必须是 `replay_pending`，分数必须为空。只有当前系统完成回放并由真人确认后，才能称为“当前系统基线”。

每个固定场景把四类数据分开保存：历史真人聊天参照、旧系统行为证据、当前系统多次回放结果、真人评审结果。旧系统曾经回复或沉默，不等于正确答案。

## 历史回复清单

```bash
python scripts/evaluate_reply_history.py
```

命令以只读方式打开 `data/cases.db`，只覆盖 `send_success = 1` 的真实发送回合，不启动 Bot、不发送消息、不调用 API。它用于整理历史问题，不是当前系统基线。

- `data/reports/reply_quality_baseline.json`：可公开的聚合基线，不含聊天身份、正文、Prompt 或人工备注。
- `data/reports/private/reply_quality_review_cases.json`：本地私有逐回合评审包，包含复核所需语境，禁止提交或公开。

其中的 AI 暂定等级只能筛选值得复核的旧回复，不能用于声称当前系统好坏。

## 迭代比较

固定同一批场景，对旧版和新版的多次回放结果做匿名、随机顺序的真人配对判断：新版更好、相当或更差，并记录回复决策、四档等级及原因。严重问题单独报告，不能用平均表现抵消。

### 固定迭代流程

每轮必须严格按以下顺序执行，任何一步未完成都不能修改下一版回复逻辑：

1. **冻结基线**：保存代码与 Prompt 的私有原文快照、代码哈希、模型、参数、场景指纹和运行配置。只有哈希、没有原文快照的历史报告不可称为可复现代码基线。
2. **重复回放**：同一版本在同一批 40 个场景上至少独立回放三次。每次使用不同结果文件，禁止把断点续跑误当成重复实验。
3. **确认稳定性**：分别比较回复/沉默决定、问题类型和质量等级。模型回复不要求逐字相同，但核心质量结论必须稳定；不稳定时先处理评测噪声。
4. **完整上下文归因**：按不必要参与、漏回复、理解对象错误、表达不自然、事实编造、旧梗或重复分类。统计只能筛查，最终判断必须查看聊天上下文和原始回复。
5. **单变量实验**：每轮只针对一个最高优先问题形成可复用假设，不允许针对单条 case 打补丁，也不允许同时叠加多个宽泛规则。
6. **隔离 A/B**：基线保持不动，实验版单独保存。被拒绝的实验不得残留在下一轮当前代码中。
7. **同场景配对评价**：A/B 使用相同模型、配置和场景，隐藏版本身份并随机左右顺序。Codex 直接评审时必须标记 `codex_provisional_not_human_ground_truth`。
8. **保守采纳**：目标问题减少、配对胜数大于负数、好评不下降、差评不增加，并且不增加严重问题、旧梗、重复或不必要参与，才可保留实验版。多次回放结论不一致时不得采纳。

当前问题优先级固定为：`是否应该参与 → 理解对象与追问 → 表达自然度 → 事实编造 → 旧梗与重复`。改善后一个问题时，前面已经通过的维度都是回归护栏，不能用更频繁插话换取内容分数。

首版历史数据只有已发送回合，因此能评价已发内容和过度参与迹象，不能测量漏回复；漏回复必须另建包含“应沉默”和“必须回复”机会的标注集。具体放行阈值应由真人基线和后续配对数据确定，不能预先编造固定百分比。

### Judge 校准指标

- 回复/沉默判断一致率。
- 四档体验等级完全一致率和相邻档容忍一致率。
- `差/严重问题` 的 Precision、Recall，严重问题 Recall 单列。
- 分歧按回复决策、体验等级、事实与边界分类保留，不能只看一个平均分。

`src/benchmarks/reply_quality_evaluation.py` 只计算已有标注的指标，不调用模型。真人 Gold、Judge 预测或经确认的通过阈值缺失时，状态分别是 `human_gold_pending`、`judge_predictions_pending` 或 `thresholds_pending`，且 `eligible_for_automatic_ab=false`。

统一评测入口：

```bash
python scripts/evaluate_reply_quality.py \
  --judge-predictions data/reports/private/reply_quality_judge_predictions.json \
  --judge-policy data/reports/private/reply_quality_judge_policy.json
```

Judge 预测逐 case 提供 `case_id`、`action`、`experience_grade`；Gold 中只有 `human_review.status=completed` 且动作、等级完整的 case 会参与计算。这样中途保存的空白模板不会污染一致率。

### A/B 判定

每个场景只允许 `实验版更好 / 当前版更好 / 相当` 三种匿名配对结论，同时分别记录两版是否出现严重问题。评价报告至少包含实验版胜率、当前版胜率、平局率、退化率和严重问题数。

只有 Judge 校准状态为 `passed`、样本量及胜率/退化率阈值已经由真人确认、且实验版没有增加严重问题时，修改才可保留。任一条件不满足都不得用均分强行放行。

A/B 比较数据逐 case 提供匿名配对结论 `preference=control|treatment|tie`，以及 `control_critical`、`treatment_critical`。通过同一命令增加 `--ab-comparisons` 和 `--ab-policy` 即可生成 A/B 门禁报告；Judge 未通过时状态固定为 `judge_not_calibrated`。

## 迭代经验与改进点发现流程

每轮不只记录可能的修改方向，还必须记录这个方向是如何被发现、证据来自哪里、是否经过独立验证。候选经验分为三类：`已验证`、`待验证`、`已否决`；训练集上的净收益只能算局部证据，不能自动升级为当前版本。

改进点按以下固定流程寻找：

1. 汇总训练集中的人工错题和版本退步，不用难分案例驱动规则。
2. 查看完整上下文和真实昵称，先区分参与决策错误与回复内容错误。
3. 用可信历史核对身份、关系和私人事实；上下文未展示不等于事实不存在，但与可信历史冲突必须视为严重问题。
4. 按群聊/私聊、应回复/可不回复、自然度/事实性分层，只有跨多个案例反复出现的错因才形成候选规律。
5. 将候选规律改写成一个可解释、边界明确的小改动，避免给单条案例打补丁。
6. 在训练集做匿名人工 A/B；Judge 只提供辅助信号，不作为事实。
7. 固定测试集只在候选定稿后验收，不从测试错题总结规则或选择 few-shot。
8. 记录收益、误伤和未解决问题；未采用的实验必须保留失败原因，防止重复尝试。

Judge 可以用于批量提名 C0 的可疑案例和初步原因，但不能直接决定错因或版本胜负。提名后必须由人工查看完整上下文，按参与错误、对象理解、显然信息复述、事实冲突、无依据解释、表达不自然等类型归因；同时从 Judge 未提名案例中保留随机抽样，避免只优化 Judge 能识别的问题。

### C0 第一轮守护规则实验

候选同时尝试了三个方向：删除对显然信息的重复解释、避免无依据的现实行动或承诺、群聊默认一句短回复。20 个已暴露训练案例人工匿名复核为候选 8 胜、基线 4 胜、8 平；群聊 6/1/7，私聊 2/3/1。

- `已验证的局部收益`：少解释显然信息、少强接结束话题、未知事实不武断判断，在群聊中有稳定价值。
- `发现方式`：聚合此前人工指出的显然信息复述、老梗复用和未知事实武断判断，再逐条查看完整上下文确认是否跨案例复现。
- `明确误伤`：现实承诺规则会误伤正常玩梗；统一的一句话限制不适合所有私聊；候选还出现了与可信历史身份冲突、编造任务限制机制的问题。
- `本轮决定`：候选整包不采用，当前 C0 不变。
- `下一小步`：保留群聊中的克制方向，但按群聊与私聊分别设边界；优先阻止可信身份事实冲突和无依据因果解释，同时保留私聊中的自然追问与互动。
