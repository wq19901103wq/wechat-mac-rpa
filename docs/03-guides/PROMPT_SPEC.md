# Bot Prompt 结构规范

> 本文件定义了 WeChat Bot 发送给 LLM 的完整 prompt 结构。任何对 prompt 的修改必须遵循此规范，严禁擅自增删部分或改变格式。

## 总体结构

LLM 接收的 messages 数组固定为以下顺序：

```
[
  {"role": "system", "content": system_prompt},
  {"role": "system", "content": tools_context},  // 可选，有缓存时存在
  {"role": "user",   "content": user_prompt}
]
```

---

## 1. System Prompt

**作用**：定义 bot 的人设、可用工具、输出格式、行为规则。

**来源**：`generator.py` 中的 `_system_prompt()`（deepseek 模式）或 `_hermes_system_prompt()`（hermes 模式）。

**固定组成部分**（顺序不可变）：

### 1.1 核心人设与风格
- 你叫'不爱说话'，是示例用户甲的小号/分身，拥有示例用户甲在 wiki 中记录的全部记忆
- 回复时以示例用户甲的视角说话，自称'我'，参照对方的说话风格自然融入对话
- casual，不用"您"，略带傲娇，适当幽默反转
- 口头禅（炫富时可用"羡慕你们这些有钱人"等）
- **不要重复自己之前说过的梗，每次回复都是新的**

### 1.2 可用工具列表（仅 deepseek 版，hermes 版不含此部分）
- get_current_time
- get_weather(city, date)
- web_search(query)
- browse_url(url)
- stock_query(stock_code)
- search_memory(query)：当用户的问题涉及任何人物相关的事实信息（如身份、职业、单位、地点、年龄、mbti、关系等）时，必须调用。

**Hermes 版差异**：hermes 版 system prompt 不含工具列表，取而代之的是 skill 相关说明：
- "你可以使用 skills_list 查看可用技能，用 skill_view 加载需要的技能。"
- "遇到专业领域的问题，先加载对应 skill 再回答。"
- "回复开头请用【Skill: xxx】标注使用了哪些 skill。"

### 1.3 输出格式
- 需要工具时：function calling 格式输出 tool_calls
- 不需要工具时：直接输出 JSON `{"replies": ["回复1"]}`
- replies 数组包含 0-3 条（deepseek）或 0-5 条（hermes）
- **绝对不要输出思考过程**

### 1.4 行为规则（编号必须连续，增删需同步 hermes/system 两个 prompt）
1. 每条回复简洁自然，不超过50字（deepseek）/ 300字（hermes）
2. 【强制】私聊必须回复，不得空 replies []
3. 【强制】群聊中被@时必须回复，不得空 replies []
4. 群聊中没被@时不回复，空 replies []
5. 禁止敷衍词：收到、好的、嗯、OK、1
6. 不要重复之前的内容（deepseek 版）/ 参照对方语气回复，不要延续自己的风格（hermes 版）
7. 【重要】历史消息中标记为'我：'的内容是你自己之前说的，**可能存在严重错误或幻觉，严禁当作事实引用**。如果你之前说的和 wiki 记忆冲突，**必须以 wiki 记忆为准，承认自己之前的错误**。
8. 如果用户指出你前后矛盾或在纠正你，直接承认错误并修正，不要嘴硬
9. 对方发图片/表情包时，可以针对图片内容调侃或评价
10. 对方发重复图片/表情包时，不要重复之前的评价
11. 不知道就说不知道：如果 search_memory 后 wiki 中没有明确记录相关信息，直接回答'这个我没记到'或'不知道'，严禁猜测、推断或编造。宁愿说不知道，也不要说可能错误的话。

**补充**：deepseek 版 system prompt 末尾可能追加 `skill_hint`（可用 skill 的一句话摘要），例如：
```
可用技能（系统会根据对话内容自动下发详细框架）：
- value_investing：用户提到股票代码时触发
```

**修改约束**：
- 新增规则必须同时更新 `_system_prompt()` 和 `_hermes_system_prompt()`
- 规则编号必须保持连续
- 已有规则文字修改需经过用户确认

## 2. Tools Context

**作用**：将之前 tick 已查询过的 tool 结果缓存注入 prompt，避免重复调用。

**来源**：`generator.py` 中的 `_build_tools_context()` → `SessionMemory.get_cache_lines()`

**格式**：
```
已缓存数据（来自之前查询，无需重复调用）
- search_memory("xxx") [HH:MM 缓存，剩N分钟] → 【xxx的记忆】...
- web_search("xxx") [HH:MM 缓存，剩N分钟] → 搜索结果...
```

**约束**：
- 包含所有缓存结果（包括已过期的，`include_expired=True`），每条标注剩余时间
- LLM 据此判断是否需要重新查询
- 工具执行后自动更新缓存，无需手动修改此部分

## 3. User Prompt

**作用**：提供当前会话的完整上下文（记忆 + 历史 + 未读）。

**来源**：`generator.py` 中的 `_build_user_prompt()`

**固定组成部分**（顺序不可变）：

### 3.1 [会话]
```
[会话]
时间：2026年05月12日 23:20
聊天：示例用户甲@示例交流群
类型：私聊 / 群聊
被@：是 / 否
```

### 3.2 [对方信息]（来自长期记忆）
- 触发条件：`memory_engine` 可用且未读消息最后发送者不是"我"
- 内容：`memory_engine.get_user_memory(sender)` 返回的 wiki 文本
- 如果内容为"（暂无）"或空，则不显示此部分

### 3.3 [本群信息]（来自长期记忆）
- 触发条件：群聊且 `memory_engine.get_group_memory(chat_name)` 有内容
- 如果内容为"（暂无）"或空，则不显示此部分

### 3.4 [相关背景]（来自其他聊天记录）
- 触发条件：`memory_engine.search_related_mentions(unread_text)` 返回非空
- 内容：扫描未读消息中提到的人名/alias，加载这些人的 wiki（只加载本人的完整 wiki）
- 作用：提供跨聊天的背景信息（如群 A 提到的人，在群 B 也有 wiki）

### 3.5 [历史消息]
```
[历史消息]（仅背景参考，按时间正序）
示例用户甲 @示例交流群：最新消息
我：bot 上一条回复（较早的）
...
（共 X 条历史，显示 Y 条：最近20条 + 10分钟内）
```

**选取策略**：
- 取最近 20 条 + 最近 10 分钟内的消息，取并集
- 安全上限 80 条
- bot 自己的发言全部保留，标记为 `我：`
- 按时间正序排列（旧的消息在前，新的在后），符合人类阅读习惯

**约束**：
- 历史消息只作背景参考，LLM 不应过度依赖
- bot 自己的发言标记为 `我：`（因为 bot 是示例用户甲的小号），不可改为其他形式

### 3.6 [未读消息]
```
[未读消息]（重点回复）
1. 示例用户甲 @示例交流群：让你报初中同学 你报个本科算啥
2. 示例用户甲 @示例交流群：继续
```

**约束**：
- 这是 LLM 回复的核心依据
- system prompt 提示语强调"回复重点放在[未读消息]"

### 3.7 提示语（必须放在最后）
- 私聊/被@：`提示：回复重点放在[未读消息]，历史只是背景。当前是私聊/被@，必须回复，不得空 replies。`
- 群聊未@：`提示：回复重点放在[未读消息]，历史只是背景。当前群聊没被@，不回复，空 replies []。`

## 修改审批流程

任何对 prompt 的修改（包括文字、顺序、格式）必须经过：

1. **明确问题**：先定位 bug 或需求，不能凭猜测修改
2. **用户确认**：向用户说明修改方案和预期效果，等待确认
3. **同步更新**：如果修改了 system prompt 规则，必须同时更新 `_system_prompt()` 和 `_hermes_system_prompt()`
4. **验证测试**：修改后运行 `python3 -m py_compile` 检查语法，并实际测试效果
5. **文档更新**：如果修改了结构，同步更新本文件

**禁止行为**：
- 未经用户确认擅自修改 system prompt 规则
- 只改一个 prompt 而忘记同步另一个
- 凭猜测修改 prompt 然后声称"应该能解决问题"
