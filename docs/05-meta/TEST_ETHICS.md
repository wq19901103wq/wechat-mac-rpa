## 测试伦理红线

### 禁止修改预期结果使测试通过

**绝对禁止**为了让测试变绿而修改 fixture 的预期 JSON、放宽断言阈值、或将错误输出写为正确预期。

**正确做法：**
- 预期 JSON 必须反映人类可理解的**正确结果**
- OCR 引擎的识别错误（如 "AI" → "Al"）应通过**测试代码中的归一化/容错层**处理，而不是修改 JSON
- 如果代码缺陷导致测试失败，必须**修复代码**，而不是修改测试标准

**违规示例：**
- ❌ 将 JSON 中的 "AI 助手" 改为 "Al 助手" 以匹配 OCR 错误
- ❌ 把 `similarity_threshold` 从 0.9 降到 0.5
- ❌ 删除失败的测试用例

**合规示例：**
- ✅ 在比较函数中加入 `normalize_ocr_errors()` 做字符映射
- ✅ 使用 LCS 相似度 > 90% 容忍 OCR 的微小偏差
- ✅ 修复 `LayoutParser` / `MessageExtractor` 的过滤逻辑

## 架构设计红线

### 基于布局判断，禁止内容启发式

**核心原则**：UI 元素的分类必须依赖**坐标、间距、颜色等布局特征**，不能依赖文本内容（如"是不是数字""像不像昵称"）。

**原因**：
- 内容启发式是脆弱的 workaround（"10" 可能是昵称、消息内容、或头像数字）
- 布局特征反映的是微信的 UI 结构，是稳定不变的

**违规示例：**
- ❌ "纯数字短文本 <=2 位不能是昵称" — 凭啥不能？群友就叫 "10"
- ❌ "包含 '收到' 的消息跳过回复" — 凭啥？用户可能真的在问"收到没"
- ❌ "文本里有 '@' 就是 @我" — OCR 可能把 'a' 识别成 '@'

**合规示例：**
- ✅ 昵称在消息上方 → 用 **y 间距 > 30px** 区分昵称和消息
- ✅ 头像数字在消息左侧 → 用 **x 坐标 < 昵称区域** 过滤噪声
- ✅ 自己的消息是绿色气泡 → 用 **颜色检测** 而非关键词匹配

## 排查流程红线

### 截图 diff 优先，调试 JSON 次之

**核心原则**：排查任何异常时，**必须先打开截图验证**，不能只看日志和调试 JSON。

**原因**：
- 调试 JSON 可能被污染（如 tick1 的 `bot_chat_name` 被 VisionPipeline 默认值覆盖为空）
- 日志只记录代码视角，截图记录真实世界
- OCR 可能识别到不存在的文字，只有截图能发现

**强制排查流程（5 步）**：

```
Step 1: 看排查文档 → 先读 RUNTIME_INVESTIGATION.md，按已有流程排查，不重新发明
Step 2: 看日志 → 定位异常 tick
Step 3: 看截图 → 验证 OCR 结果是否真实存在于窗口中（ground truth）
Step 4: 看调试 JSON → 了解 Bot 决策过程（辅助参考）
Step 5: 分层归因 → 确定问题在 Capture/OCR/Layout/Extract/Bot 哪一层
Step 6: 修复 → 在正确层级修复，禁止跨层 workaround
Step 7: 更新文档 → 把新发现的经验写回 RUNTIME_INVESTIGATION.md，形成沉淀
```

**知识沉淀闭环**：
- 排查前：先读文档，复用已有经验
- 排查后：更新文档，把新 case 写进去
- 禁止：每次排查都从 0 开始，不查阅历史文档

**违规示例：**
- ❌ 只看日志说 "chat_name 为空但发送了消息" → 误判为空 chat_name 逻辑的 bug
- ❌ 只看调试 JSON 的 `extraction_messages` → 发现不了 "Q Al模式" 是 OCR 噪声
- ❌ 凭猜测说 "可能是头像数字被当昵称" → 没有看截图确认数字的实际位置

**合规示例：**
- ✅ tick1 排查：截图显示右侧消息区全是绿色气泡（自己的消息），没有对方消息 → 根因是 OCR 噪声混入，不是 chat_name 逻辑
- ✅ tick81 排查：对比 "10" 和消息的 x 坐标（701 vs 919，差距 218px）→ 根因是聚类缺少 x 差距检查
- ✅ tick2 排查：看 "16" 的 bbox 面积（272）vs 昵称面积（3390）→ 根因是面积阈值缺失
