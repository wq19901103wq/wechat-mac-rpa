# 测试与错误守则

> 适用于：写测试、跑测试、修复 bug、验证 bug 不复发的完整生命周期。
> 
> 核心原则：**测试失败和 bug 零容忍。发现即修，修不了立即反馈。**

---

## 🚨 铁律：发现即修，修不了立即说

**任何测试失败或确认的 bug，必须在发现后立即修复。**

**如果无法立即修复**（超出当前能力范围、需要外部依赖、影响面不确定）：
- **必须立即停止当前流程**
- **必须向用户/负责人报告**：说明问题、影响范围、需要的帮助
- **禁止 silently 跳过或延后处理**

---

## 为什么这条规则不可违背

1. **识别错误 = 功能失效**：OCR 识别错误直接导致消息发送给错误的人
2. **错误会积累**：今天忽视的小问题，明天会变成难以修复的大问题
3. **影响用户体验**：发送错消息或漏消息都会严重影响用户体验
4. **破坏信任**：自动化系统必须可靠，否则不如手动操作

## 发现错误时的标准流程

```bash
# 1. 立即记录错误
python3 -c "
from tests.auto_add_error_case import auto_add_error_case
auto_add_error_case(
    image_path='/tmp/wechat_ocr.png',
    expected_result={'chat_name': '正确名称', ...},
    error_type='具体错误类型',
    error_details='详细描述'
)
"

# 2. 运行测试确认
./run_tests_v2.sh

# 3. 分析错误原因
# 查看 tests/fixtures/errors/error_*.json

# 4. 修复代码
# 修改 src/parser/ 或 src/ocr/ 逻辑

# 5. 验证修复
./run_tests_v2.sh

# 6. 提升为正式用例
python3 tests/auto_add_error_case.py --promote error_XXXXX
```

## 禁止行为

- ❌ 看到测试失败却置之不理
- ❌ 删除失败的测试用例来"修复"测试
- ❌ 修改测试标准（如把相似度从90%降到50%）
- ❌ 说"这个错误不重要"或"用户不会发现"
- ❌ 确认 bug 后不修复也不上报

## 错误分类与优先级

优先级仅用于**排序处理顺序**，不用于**决定是否修复**。

| 优先级 | 类型 | 示例 |
|--------|------|------|
| P0 | 发送者识别错误 | 把对方消息识别为自己 |
| P0 | 聊天名称识别错误 | 显示错误的聊天名称 |
| P1 | 消息内容截断 | 长消息被错误合并 |
| P1 | 消息顺序错乱 | 时间顺序不对 |
| P2 | 置信度低 | 识别但不确定 |

**原则**：P0 先处理，但所有级别都必须修。

## 测试驱动开发流程（TDD）

**任何功能开发或 bug 修复，必须遵循"先测试、后实现、再回归"的闭环。**

### 1. 开发前：先写测试
- **新增功能**：先写出能验证该功能正确性的单元测试或集成测试，此时测试应为**失败**状态。
- **修复 bug**：先将 bug 场景固化为失败测试，确认能稳定复现后再动手改代码。
- **重构代码**：先确保被重构模块已有足够覆盖的测试，或先补充测试，再进行结构调整。

### 2. 开发中：小步迭代、频繁验证
- 每完成一小步逻辑变更，立即运行**相关测试**确认方向正确。
- 禁止在大量未验证的改动上继续堆叠新代码。

### 3. 开发后：全量回归
- 功能完成或 bug 修复后，必须运行**完整的 `tests/` 套件**。
- **只有全部测试通过，才算开发完成**。任何剩余失败必须立即处理或上报。
- 提交/合并前，再次确认：`./run_tests_v2.sh` 全绿。

---

## 测试是合并的硬门槛

1. **新代码必须带测试**。没有单元测试或集成测试的新功能，不允许合并。
2. **测试必须覆盖边界条件**：空输入、异常格式、Retina/非 Retina、微信窗口未找到等。
3. **必须测试失败模式**：OCR 为空、AppleScript 超时、输入框残留、循环消息……只测 happy path 不够。
4. **CI 红线**：任何 push 到 main 之前，`tests/` 必须全绿。聊天名识别准确率 ≥95%，发送者类型识别准确率 ≥90%。

## 错误资产化

**每个 bug 都是知识资产。不只做一次修复，要构建防止复发的防线。**

修复 bug 后，必须完成以下三步才算"真正结束"：

1. **更新 `LESSONS_LEARNED.md`** — 如果属于新类型的坑，追加经验教训
2. **补充回归测试** — 如果可能复发，添加为 `tests/fixtures/errors/` 的正式用例
3. **更新当前待修复错误清单** — 将错误从下方清单移除，记录修复日期
